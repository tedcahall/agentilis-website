COA Teams: An App, Two Web Portals and an API, Built and Run by AI Agents

Course of Action runs COA Teams, a health and fitness accountability program. Members log their daily essentials, such as training, nutrition, sleep, water and stillness, and stay accountable in teams. It started as a separate spreadsheet for each member, shared with their coach. The sheets were hard to use on a phone, so members had to remember to check in when they were at a desktop. A chat bot for daily check-ins came next. Today an AI agent team builds and runs the whole platform: the iPhone and Android app, the admin portal for organizations, the customer portal, the API behind all of them, and the acceptance tests. A person approves every production release.

What the Agents Do
  1. Write the requirements as plain-language specs, and update them when the owner makes a new decision
  2. Design the screens and get the owner's approval before anything is built
  3. Build the API, the only code allowed to read or write member data
  4. Build the iPhone and Android app, test it in TestFlight and a preview channel, then ship updates over the air
  5. Build the admin portal, where organizations apply, brand the app for their members and run their teams
  6. Build billing: Apple in-app purchase on iPhone, Stripe on Android and the web, with a customer portal to manage it
  7. Run automated tests on every change, plus an acceptance suite that checks the requirements against the live API
  8. Produce illustrated videos for the course lessons and load the course content on the test system for review
  9. Read the whole code base on request and report security and quality findings, so a person decides what gets fixed
The Hard Cases
  • Two stores, two price lists: iPhone subscriptions go through Apple, and Android and web subscriptions go through Stripe. The prices differ by design, and an Apple price is never quoted for a Stripe transaction, or the reverse.
  • Names that can never change: the code repositories were renamed as the product grew, but the app's store identifiers stay fixed. Changing one would mean shipping a brand-new app.
  • Updates that must match the installed app: an over-the-air update reaches only builds on the same runtime version. On every native build the agents check whether native code changed and raise the version if it did, so an update never lands on an older install that can't run it.
  • A safety guard that looks like a failure: production deploys are blocked by default, and the hosting service reports a blocked deploy as canceled. The agents check the real deployment state, never just the newest commit, before saying anything shipped.
Guardrail

Nothing reaches production without the owner's explicit yes, every time. Production deploys of the API and the admin portal are blocked by default. The block is lifted for one approved deploy, restored right after, then checked again to confirm it is back on. App updates go to TestFlight and a preview channel first, and no store release goes out without approval. Builds come only from a clean, pushed copy of the right branch, so nothing untested ships by accident. Test data and production data live in separate databases.
