A REST API for a Decade-Old Java System, Proven Against Three Seasons of Race History

The race-weekend agents ran on screen-scraping. They built URLs by hand, logged into admin pages, and parsed the HTML to find out what had happened at the track. It worked, until a page changed. So the agent team added a real REST API to the legacy Java admin tool. No rewrite. Then we replayed three seasons of past race weekends through it, to prove it got the same answers.

Software engineering API design Regression testing

What the Agents Did
  1. James wrote the API spec first. No code until the spec was approved
  2. James built the API inside the existing Java app, sharing its database and code. No rewrite
  3. Ken locked it down: anyone can read, but only our own machines, with a secret token, can write
  4. Guido built the operator tool that runs a whole race weekend through the API
  5. Watts built the first test harness and the browser tests that guard the public pages
  6. Each replay started from a clean pre-season database and ran real weekends through the API, in race order
  7. The results were compared against the published results from those weekends
  8. Every mismatch became a fix and a new test
Guardrail

The replays never touched production. Every run started from a clean copy of the pre-season database, and loading that copy was the only direct database write allowed. Everything else went through the API, the same way a race weekend does. Race Monitor's rate limits were respected with a throttle, a backoff and the ability to resume.

What It Means for You

Which of your systems are your agents scraping instead of talking to?

Agents can work through any screen a person can. A real API makes them faster and safer, and the agents can build that API themselves, without a rewrite. Your own history becomes the test suite.
