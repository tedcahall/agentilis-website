The Person

Ted built it in 2015. Then he ran it by hand.

In 2015, Ted built marrspoints.com, a cloud points scoring system for the Washington DC Region of the SCCA. It tracks every driver, class and race in the Mid-Atlantic Road Racing Series: eight race weekends in 2026, at Summit Point, NJMP, VIR and Mid-Ohio. In 2018 the region gave Ted its Regional Executive Award for building and running it.

The Stakes

More than an hour, every race weekend, on one person's time.

The system was reliable. The process around it was not. After every race weekend, 27 official result files had to be renamed to the required format, uploaded one at a time through an admin tool, published, and confirmed. Each weekend took more than an hour of manual work, and all of it depended on one person.

Underneath were two Java applications that had been in production for more than a decade.

The Low Point
The race weekend that nearly went wrong, to come.
Rules vs. Judgment

Some of it has to be exact every time. Some of it takes a call.

Rules: exact, every time
  • Rename all 27 result files to the required format
  • Upload every file and publish the results
  • Score points the same way for every driver and class
  • Test every code change before it ships
  • Send a confirmation when the job is done
Judgment: a call on the fly
  • Process live results during the day, while racing is still going on
  • Handle gaps and imperfect data as they arrive
  • Tell provisional results from official ones
  • Process the official results after the race

Agents are most dependable on the rules. The judgment calls are the harder test, and the agent team now handles them on every race weekend.

What We Did

Five problems, each solved in production.

Day one
The agent team refactored 20,000 lines of Java on its first day on the job.
  1. Race-weekend processing is automated.
    All 27 result files are received, renamed, uploaded, published and confirmed with no manual handling. More than an hour of work per weekend now takes minutes.
  2. Legacy code is modernized.
    Both Java applications were refactored and upgraded, starting with 20,000 lines on the first day. New features have shipped since.
  3. Every change is tested before release.
    More than 60 automated Playwright and JUnit tests run on each change before it reaches production.
  4. Infrastructure is maintained.
    The AWS test and production environments are kept current, and every release is verified with smoke tests.
  5. Live race-day results are handled.
    Provisional results are processed while racing is under way, including gaps and imperfect data. Official results are published after the race.
